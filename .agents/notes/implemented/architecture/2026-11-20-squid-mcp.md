# Agent Note: Squid MCP 托管与资源授权边界

Status: implemented

## Problem

Squid 需要让通用 MCP 客户端查询部署相关数据，并沿用现有 API Key 身份和业务权限。项目、环境、项目组和空间范围的限制来自各条角色授权。逐维度合并会让原本不可见的资源进入查询结果。新增查询工具时，客户端发现的 Schema、实际处理方法和游标排序规则需要同步。

## Decision

`Squid.Api` 与 REST 在同一进程和镜像中托管无状态 Streamable HTTP `/mcp`。`Squid.Mcp` 使用官方 C# SDK 2.4.0 管理六个只读工具的协议契约和结果映射。`Squid.Core` 和 `Squid.Message` 保持独立于 MCP SDK。

- `Mcp:Enabled` 默认关闭。启用时使用专用 `X-API-KEY` 认证策略，并按 `Mcp:AllowedOrigins` 校验带 Origin 的请求。通过认证的 GET 返回 405 和 `Allow: POST`，客户端可继续通过 POST 通信。
- 工具通过请求作用域内的 Mediator 进入 Core。查询按实际资源归属验证空间、项目、项目组和环境，采用同条授权内 AND、不同授权间 OR，再执行关键词过滤、分页和成功摘要。工具不使用 `X-Space-Id`。不可见和缺失资源使用同一错误。
- MCP 查询在同一条 SQL 内读取团队成员、角色权限和各维度范围。每个维度独立聚合，使每条角色授权只返回一行。更新范围时，在事务内按团队和角色 ID 锁定目标，再原子替换三维范围。明确配置为空的维度仍表示在该维度不设限制。
- `currentReleaseVersion` 反映关联发布的当前版本。关联发布缺失时返回 `null`。最近成功摘要从完整授权范围内具备唯一任务关联的成功部署按创建时间和 ID 倒序选取。任务详情通过同一关联规则和 `TaskView` 授权查询。
- 审计从 SDK 工具处理器识别实际分发的方法，使用固定工具名和结果类别，以及调用者 ID、耗时和关联 ID。API 排除 SDK 诊断日志，Mediator 对这六种查询省略原始请求及响应。
- 输出 schema 描述成功和业务错误两种结构。游标绑定工具与查询条件，仅用于排序，后续页重新计算调用者权限。
- `Squid.Mcp` 的 `Tools` 按资源发现、发布版本、部署及任务组织。工具组的注册项关联工具声明、处理方法以及适用的游标排序，显式注册目录供工具发现、调用分发和审计共用。
- `Squid.Api` 的 `Extensions/Mcp` 集中管理 HTTP 端点注册、启动过滤及请求审计。MCP 端到端测试按端点、工具调用和审计组织，共用独立的 fixture 和 API 测试宿主。

## Alternatives considered

- **在 Squid.Api 中实现所有工具**。工程文件较少。独立类库让工具契约与宿主职责各自演进，同时保留同进程认证和调用。
- **独立 MCP 服务或本地适配器**。可独立部署。它会增加凭证传递、部署单元与 REST 兼容成本，首版采用同进程 HTTP 托管。
- **OAuth 登录**。覆盖只接受 OAuth 的客户端。首版沿用现有 API Key 的签发、撤销和授权数据，降低部署配置成本。
- **按 Schema、调用分发和游标分别维护工具清单**。同类协议实现集中，但每个分页工具都要求三处同步。工具组就地维护会一起变更的声明和处理规则。

## Consequences

运维通过现有 API 发布流程启用 MCP，业务团队沿用 Squid 角色范围。宿主需能注册 API Key 方案，客户端需支持配置 HTTP 请求头。独立类库增加一条项目引用，查询需要加载逐角色范围。每个工具都需要在对应的工具组显式注册，增加工具时可以就地核对其协议契约与执行逻辑。接入要求和实测覆盖见 [MCP 使用指南](../../../../docs/mcp.md)。
